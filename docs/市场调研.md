# Chunkly 市场调研与去留判断

> 调研日期：2026-10-20
> 调研方式：Chrome 应用商店实页核查、竞品官网/仓库核查、学术文献检索、以及对本项目的一次真实 LLM 线上实测（用仓库 `.env` 里的 GLM Key，见第 4 节）。
> 可信度标记：**实测** = 我自己跑出来的数据；**实页** = 我亲自打开页面看到的；**第三方** = 只有二手来源，标注出处但未独立验证。

---

## 0. 一句话结论

**不建议作为独立产品继续投入。** 可以继续投入，但必须换定位——从"意群切分查看器"换成"有反馈、可测量的阅读训练闭环"。

三条最硬的证据：

1. **直接竞品已经存在，且只有 41 个用户。** 这同时否证了两件事：市场是空的（不是），和这个需求很大（也不是）。
2. **本产品唯一的差异化假设（"LLM 切分显著优于规则"）在交付版本中不成立**，我实测发现它在真实输入上退化成按句切分。可用 prompt 修好，但修好之后它就是一段 prompt——一下午能被抄走。
3. **架构上它严格劣于已有的免费方案**：需要用户自备 API Key、每次调用 2.5 秒、免费额度实测 75% 概率撞 429；而竞品在本地跑、0 延迟、0 成本、不要 Key。

| 版本 / 更新日 | v2.2.1 / 2026-07-08（距今约 3 个月） | **实页** |
| 安装量 | **41 users** | **实页** |
| 评分 | 5.0，**2 个评分** | **实页** |
| 体积 | 826 KiB | **实页** |
| 切分方式 | **本地运行，"Text chunking runs locally in the extension"，不发文本到任何服务器** | **实页** |
| 切分技术 | `compromise.js` + 确定性短语规则（不是 LLM） | **实页**（GitHub 仓库说明） |

| 功能 | TempoLeaf | Chunkly |
|---|---|---|
| 网页面内标注意群边界 | 有 | 有 |
| **RSVP 聚焦播放**（一次只显示一个意群，空格暂停、左右键跳转） | 有 | 无 |
| **贴入文本阅读器**（PDF/字幕/笔记） | 有 | 无 |

| 键盘快捷键 | 有（Ctrl/Cmd+Shift+S / +E） | 无 |
| 界面语言 | 英 / 繁中 / 日 | 仅中文设置页 |
| 需要 API Key | **不需要** | 需要 |
| 需要联网 | 不需要 | 需要 |
| 单次延迟 | 本地，毫秒级 | **实测 2.4–2.5 秒** |
| 单次成本 | 0 | 用户自付 token |
| 额度限制 | 无 | **实测 75% 概率撞 429** |

**判断**：Chunkly 目前是 TempoLeaf 的一个功能子集，且在每一个"可用性"维度上更差。这是最需要正视的事实——不是"我们的模型更好"，而是"用户为什么要忍受 Key、等待、限流，去换一个功能更少的版本"。

> 注：TempoLeaf 自己的 README 也诚实承认规则法的局限（"unusual syntax, ambiguous phrasing, names, citations... can still lead to awkward chunk boundaries"）。这正是 LLM 的潜在空间所在——但它需要被证明，而不是被假设。见第 4 节。

## 2. 相邻竞品：谁能在一天内把这个功能吞掉

| 产品 | 用户规模 | 业务模式 | 加意群功能的难度 |
|---|---|---|---|
| **沉浸式翻译** | 官网自述 **3000 万+ 用户**（**实页** immersivetranslate.com） | 免费 + Pro/Max 订阅（第三方口径约 $9.99/$34.99 每月，**未独立验证**） | **很低**。它已经做整页 DOM 改写、已有 LLM 通道、已有用户。加一个"按意群断句高亮"是一个开关。 |
| Language Reactor / Trancy / Migaku | 大（字幕学习类头部） | 订阅 | 低。它们已经做"逐句/逐词"粒度控制，加"意群"粒度是同一套机制 |

## 3. 需求侧：这是真痛点，还是教师视角的抽象？

### 3.1 学术证据：方向对，效应量弱，且多为"教学方法"而非"工具"

| 研究 | 结论 | 强度 | 来源 |
|---|---|---|---|
| 韩国 EFL 大学生（口语/默读双条件） | 意群切分能力与阅读理解**相关** | 相关性研究，非因果 | koreascience.kr/article/JAKO201003939212472.pdf |
| 日本 EFL 中学生，Chunk Reading Training（4 周，每周 3×15 分钟） | 语法判断测试提升约 10%，但**组间差异无统计显著性** | 效应弱 | ERIC EJ1399504 |
| IJSMS 2023，chunking 策略教学 | 前后测显著提升 | 教学方法研究，样本与设计未细核 | ijsmsjournal.org/2023/volume-6 issue-1/ijsms-v6i1p107.pdf |
| "Improving L2 Reading Efficiency Through Chunk-Based Reading: An Eye-Tracking Investigation" | 眼动研究，存在 | **未能获取正文**（ResearchGate 反爬拦截），不下结论 | researchgate.net/publication/387334334 |

**诚实的读法**：意群训练"不是伪科学"，但也**不是被强证据支撑的杠杆**。最强的结果也只是"语法加工略有改善且不显著"。这不足以支撑"这是一个值得做的产品"的判断。

### 3.2 用户侧的痛点是"读得慢/读不懂"，不是"我看不见意群边界"

搜索到的中文内容（ReadSavor、知乎、公众号、各级教学博客）几乎全部在讲**方法**（用斜杠自己划意群、跟读、影子练习），而不是在求**工具**。这说明：

- 痛点真实存在：逐词阅读、卡在生词上、句子读完忘了前半句——这些抱怨非常普遍。
- 但用户把它归因为"词汇量不够 / 没养成习惯 / 材料太难"，**不归因为"缺少一个能标出意群边界的工具"**。
- 因此这是个**未被用户认知为产品**的需求。教育用户的成本极高，而这类产品恰恰没有预算做这件事。

对照：能活下来的阅读类学习工具（Readlang、LingQ、Relingo、Burning Vocabulary、沉浸式翻译）卖的都是**即时可感知的价值**——"点一下就懂这个单词/这句话"。意群高亮卖的是**延迟回报**——"坚持几周你会读得更快"。后者的转化率天然低一个数量级。

### 3.3 付费意愿

- 语言学习工具普遍能收到 **¥25–70/月**（Readlang、LingQ、Trancy、Toucan 等）。**市场存在。**
- 但付费点几乎都是"词典/翻译/复习/跨端同步"，不是"切分"。
- 本产品当前形态**没有任何可收费的东西**：没有服务器成本可转嫁、没有内容库、没有账户体系。即便定价，用户也会问"我为什么不直接用免费的 TempoLeaf"。

## 4. 实测：LLM 方案到底成不成立（本次调研的原创数据）

这是设计文档里标注的最大已知限制（"未做真实 LLM 在线集成测试"）。我用仓库 `.env` 里的 GLM Key 把它补上了。

### 4.1 实验一：现有 prompt 在真实输入上退化成"按句切分"

**输入**：一段 672 字符、119 词的正常英语段落（约 4 句话），模型 `glm-4.7-flash`（即插件预设的模型），`temperature=0`。

**输出**（成功的那一次）：

```
Reading in phrases is not a trick you can switch on. / It is a habit built by repeated exposure to text ... / When learners meet an unfamiliar word, ... / ...
```

共 6 段，**平均 112 字符 / 约 20 词一个 chunk，切点全部落在句号**。

**这是致命的**：产品的全部主张是"按意群而非逐词/逐句阅读"，而模型给的就是**逐句**。对学习者来说，"把句子按句号切开"提供的信息量是 0——他本来就看得见句号。

根因在 prompt：`buildSystemPrompt()` 全篇是描述性的（"像母语者说话时那样分组"），**没有一个可执行的约束**——没有字数区间、没有 few-shot 示例、没有"整句不是合法 chunk"的禁令。LLM 在这种模糊指令下会选择最保守的输出，即按句切。

### 4.2 实验二：加一条硬约束就能修好——所以差异是可被抄的

把 system prompt 换成"每个 chunk 必须 2–6 词，不得超过 8 词，整句不合法"+ **一个 few-shot 示例**，同一模型、同一输入：

```
Reading in phrases / is not a trick / you can switch on. / It is a habit / built by repeated exposure / to text that is / just slightly harder than / what you can already / handle comfortably. / When learners meet / an unfamiliar word, / they often stop, / decode it letter / by letter, and / lose the thread / of the sentence.
```

| 指标 | 现有 prompt | 加约束的 prompt |
|---|---|---|
| chunks 数 | 6 | 16 |
| 平均词/chunk | ~20 | **3.4** |
| 最大词/chunk | ~22 | 4 |
| 延迟 | 2492 ms | 1851 ms |

**这正是意群该有的样子。**这说明：
- 好消息：LLM 路线**技术上可行**，且质量明显好于"按句号切"。
- 坏消息：修好它的全部内容是**一段 prompt 加一个例子**。这不构成任何壁垒，而 TempoLeaf 的 41 用户证明"能把意群切对"本身不值钱。
- 仍需人工审查：`decode it / letter by letter` 切开了一个固定搭配，`to text that is / just slightly harder than` 切断了比较结构。**质量是"体面"，不是"优秀"**，且没有客观评测集能证明它比 compromise 规则法好多少。

### 4.3 实验三：免费额度不可用——这是当前形态的致命伤

对 672 字符的输入连续请求 4 次，`glm-4.7-flash`：

| 次数 | 结果 |
|---|---|
| 1 | ✅ 2492 ms |
| 2 | ❌ HTTP 429，错误码 1305「该模型当前访问量过大」 |
| 3 | ❌ HTTP 429 |
| 4 | ❌ HTTP 429 |

另一轮 3 次请求中 1 次 429。另一次单句测试中，3 次里 2 次 429。

**成功率约 25%–65%，且不可预测。**而插件侧**没有实现任何重试**（交付文档 6.5 节自己承认了：`retryable` 字段算好了但没用）。用户实际体验是：右键 → 等 2.5 秒 → `alert("触发速率限制，请稍后再试")`。

再加上：
- 每次切分 **2.5 秒**（这还是 672 字符；一整篇文章会到几十秒）。阅读工具需要的是 <100ms 的即时反馈，2.5 秒的阻塞是品类级的错误。
- 同一段文本重复切分要重复付费、重复等待，没有缓存。
- 实测 `concat == original` **为 false**，即"字符级完全可复原"这条硬性契约在真实输出下不成立（当前靠 `indexOf` 兜住了 offset，但契约本身已经破了）。

### 4.4 实验结论

> **"LLM 切分质量显著优于规则引擎"这个立项理由，在交付版本中不成立；修正后成立，但修正成本是一段 prompt，不构成产品价值。**

立项文档 2.3 节写"不做本地小模型/规则兜底……本身就是想验证 LLM 方案的效果"。**这个验证现在做完了，结论是：差异存在但没有大到能支撑一个产品，而代价（Key、2.5 秒、75% 失败率、用户自付费）远大于收益。**

## 5. 技术路线对比（这决定了"如果要做，该怎么做"）

| 路线 | 延迟 | 成本 | 需要 Key | 质量 | 备注 |
|---|---|---|---|---|---|
| 云端 LLM（当前实现） | **实测 2.5 s** | 用户自付 | 是 | 加约束后体面 | 免费额度实测多 429 |
| 规则 + `compromise.js`（TempoLeaf 做法） | 毫秒 | 0 | 否 | 长难句/专名会崩 | 已开源 MPL-2.0，可直接对比 |
| **Chrome 内置 Prompt API（Gemini Nano）** | 本地 | **0** | **否** | 小型模型，可能弱于 GLM | **关键变化，见下** |
| 本地微调小模型（ONNX/WebGPU） | 本地 | 0 | 否 | 取决于训练数据 | 需自建标注集，成本最高 |

**必须知道的一个平台变化**：Chrome 的 **Prompt API 自 Chrome 138 起对扩展稳定可用**，由设备端 Gemini Nano 驱动，离线运行、无 token 成本、无需 API Key（来源：`developer.chrome.com/docs/ai/built-in`、以及 chromiumembedded/cef issue #3982 对 Chrome 文档的引用，**实页**）。

这对本项目的含义是双面的：
- **利好**：抹掉了"必须让用户去 bigmodel.cn 申请 Key"这个最大转化杀手，也抹掉了延迟和费用。
- **利空**：它同时对所有人可用。**"我们用了 LLM"不再构成任何差异化**，因为浏览器自己就把 LLM 免费发给每个用户了。差异化会重新回到"谁的 prompt / 谁的训练数据 / 谁的闭环设计更好"——而这些都不是本项目的现有资产。

## 6. 平台与合规风险（不是主要矛盾，但需要知道）

- MV3 禁止远程代码，全部 JS 必须打包进扩展。当前实现合规（**实页** 构建产物检查）。这意味着 prompt 改动必须发版，无法服务端热更新——prompt 迭代的反馈闭环会明显变慢。
- Chrome Web Store 用户数据政策要求"传输浏览内容必须是为用户可见功能所必需，并在商店页明确披露"。把用户选中的网页文本发给第三方 LLM 属于需披露项；`<all_urls>` 式的宽权限在审核中会被额外审视。
- 反过来看：**本地运行（TempoLeaf / Gemini Nano）在隐私叙事上是压倒性优势**，尤其在教育/未成年人场景。当前"把网页文本发给智谱"在 ToB/校园渠道基本是硬障碍。

## 7. 如果继续做：迭代方向（按"是否影响生死"排序）

当前实现是一个**技术骨架**（engine 分层干净、错误分类完整、19+9 个测试、offset 对齐用游标 `indexOf` 而非让模型数位置——这些设计是对的，值得留着）。问题不在工程质量，在**产品定位**。

### P0：先做减法，验证还要不要做（1 天）

1. **用同一批句子，把当前 prompt、修正后的 prompt、`compromise` 规则法三方并列跑一遍，人工标注哪条更好。** 需要至少 50 句，含长难句、专名、比较结构、并列。如果 LLM 没有明显胜出，**项目到此为止**，这个结论本身就值得写成一篇文章。
2. 打开 `thinking: {type:"disabled"}` 之外再测一次 `enabled`，看质量/延迟权衡（我这次被 429 挡住了，没测成）。

### P1：如果要做，先把"不可接受的体验"消灭（1–2 周）

3. **换成本地推理**：优先接 Chrome Prompt API（无 Key、无成本、无延迟）；`engine/client.ts` 只需新增一个 provider 类型，`prompt.ts` 完全复用。这一步同时解决 429、延迟、隐私、转化四个问题。
4. **分级降级链**：本地规则先秒出结果 → LLM 异步覆盖修正。读文章的人不能等 2.5 秒看空白。
5. **缓存**：按文本 hash 缓存切分结果（`chrome.storage.local`）。同一篇文章只切一次。
6. **修掉陪伴性缺陷**：loading 态、快捷键触发、失败重试（`retryable` 已经算好了，接上就行）、跨段落选区。这些是及格线，不是加分项。

### P2：真正的差异化——从"查看器"变成"训练器"

这是唯一可能让产品活下来的方向。核心逻辑：**切分只是输入，价值在反馈和进展。**

7. **可测量的结果**：阅读速度（WPM）+ 理解题正确率，前后对比。没有"训练前后我变快了 X%"的数字，用户无法感知价值，也就不会付费，也不会留存。
8. **自适应粒度**：按用户水平调 chunk 大小（生词多 → 细粒度；水平高 → 粗粒度）。这是让 LLM 真正不可替代的地方——规则引擎做不了个性化。
9. **最小闭环**：读 → 标出卡住的意群 → 次日复现这些意群 → 记录"这个意群我掌握了吗"。这一步把它从工具变成习惯，才可能有留存。
10. **别做生词本**。那片红海（Relingo、Burning Vocabulary、LingoWay、沉浸式翻译）已经饱和，且和"意群"是两个心智。

### P3：选题材，别做通用工具

11. 通用"任意网页"是伪需求，会把你拖进和 TempoLeaf / 沉浸式翻译的正面对撞。**选一个窄口**：
    - 考研/雅思/托福**长难句**拆解（有明确付费意愿、有明确材料、有明确痛点"这句我看不懂"）；
    - 或**教师侧**：给老师做"一键给这篇课文标注意群"的备课工具（ToB，愿意为效率付费，且不在意 2.5 秒延迟）。
    - 教师侧尤其值得考虑：它把延迟和成本从"不可接受"变成"可接受"，且避开了 C 端获客。

---

## 8. 结论

### 还有没有继续开发的价值？

**作为独立 C 端产品：没有。**依据按权重排序：

1. **需求未被验证，且已有反证**。直接竞品 TempoLeaf 上线至今 41 个用户。这不是"市场空白"，这是"市场投票结果"。
2. **唯一的差异化假设不成立**。立项理由是"LLM 比规则好"，实测交付版本退化成按句切分；修好后只是 prompt，而 TempoLeaf 的核心已 MPL-2.0 开源，可被直接对比与超越。
3. **架构性劣势压过一切功能优势**。Key + 2.5 秒 + 75% 限流失败率 + 用户自付费，任何一条都足以让留存归零。
4. **功能易被吞并**。沉浸式翻译 3000 万用户、已有 LLM 通道和 DOM 改写能力，加这个功能是一个开关的成本。
5. **它不是产品，是一个功能**。没有账户、没有数据、没有闭环、没有可收费的东西。

**作为"训练闭环"或"教师工具"：有条件地有。**条件见 P2/P3——必须换定位、换推理位置（本地）、换目标用户（窄口 + 愿付费）。

**作为学习/作品集项目：有，而且已经值了。**engine 分层、错误分类、游标 `indexOf` 做 offset 对齐（而不是让模型数位置）——这几个判断都是对的，而且是很多人会做错的。这份代码可以留着，也可以作为"我用 LLM 做过一个产品并诚实评估了它"的完整案例。

### 最强的三个反驳（如果你还想继续）

1. **41 用户可能只是没做推广，不代表需求不存在。** 有效——但反过来说，如果推 41 个用户都需要解释，那获客成本就是你算不过来的账。
2. **TempoLeaf 的规则法在长难句上确实会崩，LLM 有真实空间。** 这是本项目唯一的技术立足点。**但它需要被量化证明**（P0-1），不能靠"规则法有局限"的直觉。
3. **意群只是第一步，后面接听说训练可以做大盘子。** 这是唯一有想象力的路径——但那意味着你要做的其实是字幕君/Echo Loop 那类产品，切分是其中一个模块，而不是全部。

### 最窄的可行切入点

> **给考研/雅思长难句做"意群拆解 + 逐块对照理解"的单一场景工具，本地推理，不要 Key。**
>
> 一句话验证：能不能让一个有 3 个月备考压力的学生，在看到一句 60 词的从句套从句时，3 秒内看懂它的结构。这一个场景成立，产品成立；不成立，就不该继续。

### 建议的下一步（今天就能做）

先做 **P0-1**：50 句三方对比（现有 prompt / 修正 prompt / compromise 规则）。这是一个下午的工作量，产出一个表，然后决定是继续还是归档。**不要先做 UI，也不要先搭后端。**
