# Chunkly 交付文档

## 1. 产品概述

Chunkly 是一个浏览器插件：用户在网页上选中英文文本，插件调用 LLM API 把文本按「意群」（phrase chunk）切分，并在原网页 DOM 上用颜色高亮标注，帮助英语学习者按意群阅读而非逐词阅读。

产品定位、调研结论详见 [docs/意群切分Engine设计方案.md](../意群切分Engine设计方案.md)。本文档记录**实际交付的实现**、与设计方案的差异、安装配置方式、以及已知限制。

## 2. 架构

Monorepo（pnpm workspace），两个包：

```
chunkly/
├── packages/engine/    # 意群切分核心逻辑，纯 TS，不含浏览器专属依赖
└── apps/extension/     # 浏览器插件（MV3），依赖 engine
```

### 2.1 packages/engine

对外只有一个函数：

```ts
chunk(text: string, options: { provider: ProviderConfig; granularity?; signal? }): Promise<ChunkResult>
```

内部结构：

| 文件 | 职责 |
|---|---|
| `prompt.ts` | 构造 system/user prompt，要求 LLM 只在原文中插入分割点，不改写文本 |
| `client.ts` | 调用 OpenAI 兼容协议的 `/chat/completions`，把 HTTP 状态码 / fetch 异常映射成统一错误码 |
| `parse.ts` | 把 LLM 返回的 JSON（`{"chunks": ["...", "..."]}`）定位回原文的 `startOffset`/`endOffset` |
| `errors.ts` | `ChunkEngineError` 类 + 错误码 -> 是否可重试 的映射 |
| `index.ts` | 组装以上模块，对外暴露 `chunk()` |

**offset 对齐算法**（设计方案第 4.2 节要求的关键点）：不要求 LLM 输出数字 offset（LLM 数字符位置不可靠），而是要求它输出「按意群切分后的原文子串数组」。engine 侧维护一个游标，对每个子串做 `originalText.indexOf(chunkText, cursor)` 顺序查找来定位 offset，找到后游标前移。如果某个子串在游标之后找不到（说明 LLM 改写/复述了文本），直接抛 `INVALID_RESPONSE`，不做模糊匹配兜底。

**错误分类**（HTTP 状态码 -> 错误码）：

| HTTP 状态 | 错误码 | retryable |
|---|---|---|
| 401 / 403 | `AUTH_FAILED` | false |
| 429 | `RATE_LIMITED` | true |
| 408 | `TIMEOUT` | true |
| 5xx | `SERVICE_UNAVAILABLE` | true |
| 其他非 2xx | `INVALID_RESPONSE` | false |
| fetch 抛 `AbortError` | `TIMEOUT` | true |
| fetch 抛其他异常 | `NETWORK_ERROR` | true |
| 响应体解析失败 / chunks 定位失败 | `INVALID_RESPONSE` | false |

测试：`packages/engine/test/index.test.ts`，19 个用例覆盖上述每一种分类 + 3 种成功路径，全部 mock `fetch`，不依赖真实 API Key。

### 2.2 apps/extension（MV3）

```
manifest.json          # background/content_scripts/options_page 声明
src/
  types.ts             # StoredSettings 类型 + GLM_PRESET/DEFAULT_SETTINGS
  storage.ts           # chrome.storage.local 读写 + 纯校验逻辑 normalizeSettings
  highlight.ts          # computeSegments（纯函数，可测）+ applyHighlight（真实 DOM 操作）
  content.ts           # 监听触发消息 -> 取选中文本 -> 调 engine.chunk -> 高亮
  background.ts        # 右键菜单注册/点击 -> 给 content script 发消息；处理自定义域名权限申请
  options.ts           # 设置页表单逻辑
options.html            # 设置页 UI
```

构建：三个独立 Vite config（`vite.options.config.ts` / `vite.content.config.ts` / `vite.background.config.ts`），分别产出：
- `options.html` + `assets/*.js`（标准 ES module 页面）
- `content.js`（IIFE，无 import/export 语句 —— MV3 content script 不支持模块化脚本）
- `background.js`（IIFE，同上原因）

`scripts/copy-manifest.mjs` 把 `manifest.json` 复制进 `dist/`。构建命令：

```bash
pnpm --filter @chunkly/extension build
```

产物在 `apps/extension/dist/`，可直接作为 unpacked extension 加载。

## 3. 与设计方案的重要偏离

设计方案 2.2 节写的是「默认内置智谱 GLM 免费 API，用户免配置即可使用」。**实际交付并未内置任何真实可用的 API Key**，原因：

1. 真实可用的密钥硬编码进公开分发的插件代码里，任何人解包 `dist/content.js` 都能提取出来，会被滥用到超出预期的调用量，账号持有者（不管是谁）要承担后果。这是一个真实的密钥泄露风险，不是可以靠"混淆"缓解的问题。
2. 我本身也没有一个可分发的真实 GLM API Key。

**实际实现**：「GLM 预设」在设置页中是一个**预填 baseURL + model 的快捷选项**（`https://open.bigmodel.cn/api/paas/v4/` + `glm-4.7-flash`），选中后仍需要用户自己去 [bigmodel.cn](https://bigmodel.cn) 申请 API Key 并填入。「自定义 Provider」选项让用户填入任意 OpenAI 兼容的 baseURL/apiKey/model（可用于 OpenAI/Claude/Gemini 的兼容层）。

如果产品上线后要真正做到「免配置」，需要后续补一个服务端代理（插件调用你自己的后端，后端持有密钥并做用量限制），而不是把密钥直接放进客户端代码——这是一个需要额外基础设施投入的决策，本次交付未包含。

## 4. 安装与使用

### 4.1 构建插件

```bash
pnpm install
pnpm --filter @chunkly/engine build
pnpm --filter @chunkly/extension build
```

### 4.2 加载到 Chrome

1. 打开 `chrome://extensions`
2. 打开右上角「开发者模式」
3. 点击「加载已解压的扩展程序」，选择 `apps/extension/dist` 目录

### 4.3 配置 API Key

1. 点击插件图标 -> 右键「扩展程序选项」（或在 `chrome://extensions` 里找到 Chunkly 点「详情」->「扩展程序选项」）打开设置页
2. 选择「使用 GLM（智谱）」或「自定义 Provider」
   - GLM：去 [bigmodel.cn](https://bigmodel.cn) 控制台申请 API Key，填入「API Key」字段即可，baseURL/model 已预填
   - 自定义：填入你自己的 OpenAI 兼容 baseURL + apiKey + model（如 OpenAI/Claude/Gemini 的兼容层地址）
3. 点击「保存」。若填的是自定义域名，插件会向浏览器申请该域名的访问权限（需要用户在浏览器弹窗中确认）

### 4.4 使用

1. 在任意网页选中一段英文文本
2. 右键菜单选择「用 Chunkly 切分选中文本」
3. 插件调用配置好的 LLM，把选中文本替换为带高亮色块的意群分割结果

## 6. 已知限制

1. **不内置真实可用的免费 API Key**（见第 3 节），用户必须自备 API Key 才能使用插件的任何功能。
2. **未做真实 LLM API 的在线集成测试**。engine 的 HTTP 调用逻辑、错误分类只在 mock fetch 下验证过；真实 GLM/OpenAI 接口的返回格式如果和 OpenAI Chat Completions 协议有细节出入（例如某些 provider 不支持 `response_format: {type:"json_object"}`），需要用真实 Key 跑一次才能发现。
3. **选区限制**：`content.ts` 用 `window.getSelection()` 取第一个 Range，只处理单一连续选区；跨多个不连续区域的选择、表单控件内部的选中文本（如 `<textarea>`/`<input>`）不支持。
4. **不支持流式响应**：每次切分是一次完整的请求-响应，长文本可能等待时间较长，没有做加载态之外的进度反馈（当前只有浏览器原生 `alert` 报错提示，没有 loading UI）。
5. **没有重试逻辑**：`ChunkEngineError.retryable` 字段已经计算好，但插件侧目前只是把错误提示给用户，不会自动重试——自动重试策略在设计方案第 6 节里标注为"待定"，本次未实现。
6. **右键菜单是唯一触发方式**：没有做快捷键触发或者浮动按钮触发，设计方案里也没有强制要求，但如果用户期望更多触发方式，需要后续迭代。
7. **Firefox/Safari 未验证**：manifest 是标准 MV3 格式，理论上 Firefox 113+ 支持，但只在 Chrome (Chrome for Testing 149) 上做过验证。
8. **没有做 `optional_host_permissions: ["<all_urls>"]` 在真实用户交互下的授权流程验证**：代码逻辑上会在保存自定义 baseURL 时调用 `chrome.permissions.request`，但这一步依赖浏览器原生权限弹窗，自动化脚本无法验证弹窗后用户点击"允许"的完整链路，只验证了消息能正确从 options 页发到 background。

## 7. 后续建议的优先级（如果继续迭代）

1. 找一个真实 GLM API Key 跑一次线上集成测试，确认 prompt/解析逻辑在真实模型输出下成立
2. 如果要做到"免配置即可用"，评估搭建一个轻量后端代理来托管密钥
3. 补充 loading 态和更友好的错误提示 UI（目前是浏览器原生 `alert`）
4. 增加快捷键/浮动按钮等更多触发方式
