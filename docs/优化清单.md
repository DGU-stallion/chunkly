# Chunkly 优化清单（第一性原理视角）

> 日期：2026-10-20
> 前置阅读：`docs/市场调研.md`（结论：作为独立 C 端产品没有价值，建议换定位）
> 本文回答的是另一个问题：**如果继续做，从第一性原理看，还有哪些优化？**

---

## 0. 先问：这个系统真正要交付的是什么？

把这个产品剥到最里层，它承诺的只有一件事：

> **让读者在 100ms 内、在原文位置上、看到「按意群分组」的视觉提示，且原文一个字都不能变。**

注意这句话里有三个不可让步的约束：**快**（100ms 量级）、**原位**（不能跳去另一个阅读器）、**无损**（不能改写文本）。所有优化都可以拿这三条来打分。

对照现实：

| 约束 | 现状 | 差距 |
|---|---|---|
| 原位 | ✅ 原文 DOM 高亮 | 已满足 |
| 无损 | ✅ 游标 `indexOf` + 段拼回 + 空白归并 | 已满足，且有 39 个测试守着 |
| **快** | ❌ **1.9–2.6s（单句）/ 3–16s（长文）** | **差 20–100 倍** |

**所以第一性原理下的唯一真问题是：为什么一个阅读辅助工具要等 2 秒？**
其余所有优化（UI、闭环、多端）都在这个问题之下。

---

## 1. 延迟的物理下限：拆开每一毫秒

实测一个 297 字符请求 1967ms（`effort=off`、0 reasoning token、输出约 100 token）。这个数字本身就是诊断：

- 一个 flash 级模型生成 100 token，正常应该 300–600ms。
- 所以 **约 1.4–1.7s 花在别处**：网络 RTT、网关排队、Provider 调度。
- 这也解释了为什么并发只提速 1.1–1.25×：**并发摊薄不了固定开销**，而固定开销才是主体。

推论（这就是第一性原理给出的答案）：

| 方案 | 理论延迟 | 能否满足 100ms | 结论 |
|---|---|---|---|
| 调 prompt / 换模型 | 1.5–4s | ❌ | 只改常数，不改数量级 |
| 分段并发 | 1–16s | ❌ | 已做，解决的是可靠性不是延迟 |
| 流式渲染（streaming） | 首字节 300–500ms | ⚠️ 接近 | **性价比最高的延迟优化** |
| 缓存（同文本复用） | 0ms | ✅ | 阅读场景重复率高，命中率可观 |
| 规则法秒出 + LLM 异步覆盖 | 首屏 <10ms | ✅✅ | **唯一能满足 100ms 的架构** |
| Chrome 内置 Prompt API（Gemini Nano） | 本地，100–500ms | ⚠️ | 无 Key、无网络、无成本 |

**结论：延迟这个问题在"云端 LLM 单次阻塞调用"这个架构里无解。要么改架构（本地/规则兜底），要么改交互（流式）。**

## 2. 优化清单（按"是否影响生死"排序）

### P0 — 影响生死

#### P0-1　用规则法先秒出，LLM 异步覆盖（架构级）

这是唯一能同时满足"快"和"准"的方案，也是我上一轮调研里已经点出但没实现的方向。

```
点击/选中
  └─ <10ms：规则法（compromise + 标点/虚词规则）先渲染一版
       └─ 后台：LLM 切分完成 → 平滑替换为更准的版本
```

- 用户立刻看到东西，感知延迟 <10ms。
- LLM 慢不再是缺陷，而是"渐进增强"。
- 顺带解决离线、断网、Key 失效、429 全部场景——**降级路径天然存在**。
- 成本：需要引入 `compromise`（TempoLeaf 用的同一个库，MPL-2.0，可参考其规则）。
- **这是我认为最该做的下一步。**

#### P0-2　流式渲染（如果只做一件事就做这个）

`client.ts` 目前是 `await response.json()`，第一个字都看不到。改成 SSE 读取 `delta.content`，边收边解析 `{"chunks":[` 后的每个字符串，收到一个渲染一个。

- 首个意群出现时间从 1967ms → 约 400ms。
- 对"阅读辅助"这种渐进消费的场景，感知体验提升远大于数字。
- 需要改写 `parse.ts` 为增量解析器（状态机，容忍不完整 JSON）。
- 注意：`response_format: json_object` 与流式可共存，但部分 Provider 不支持，需 fallback。

#### P0-3　缓存（1 小时工作量，收益最大）

阅读场景的重复率被严重低估：同一篇文章反复打开、翻页回来、同一段被重新选中。

- 以 `hash(text + model + effort + granularity)` 为 key，存 `chrome.storage.local`。
- 命中即 0ms、0 成本。对"读一篇文章"这个场景，命中率会很高。
- 需要注意：`chrome.storage.local` 默认 10MB（`unlimitedStorage` 可解），要设 LRU 上限。

### P1 — 及格线（现在缺的）

| 项 | 现状 | 说明 |
|---|---|---|
| **流式/加载态** | 只有 toast「切分中…」 | 无法取消，无进度。需要 AbortController 接到 UI 上 |
| **快捷键触发** | 只有右键菜单 | `chrome.commands` 加一条，5 行代码 |
| **重试** | engine 内部有，插件侧无 | 已被并发路径覆盖；短文本路径仍无重试 |
| **跨段落/多行选区** | 只取第一个 Range | 阅读场景里跨段落选中是常态，当前静默失败 |
| **切换粒度** | `granularity` 在 engine 有，UI 没有 | 一行设置项 |
| **清除高亮** | 没有 | 用户标完想还原，现在只能刷新页面 |
| **撤销** | 没有 | `range.deleteContents()` 是有损操作，改坏了无法恢复 |

#### 一个必须正视的实现缺陷

`highlight.ts` 的 `applyHighlight` 用 `range.deleteContents()` + `insertNode()` **替换了原始 DOM 文本节点**。

后果：
1. 破坏了页面自身的 DOM 结构（React/Vue 站点可能重渲染导致错乱）。
2. 无法撤销（原始节点已销毁）。
3. 对 `contenteditable`、React 受控组件、Shadow DOM 会出问题。

更稳的做法：不删节点，用 `Range.surroundContents()` 或对文本节点做 `splitText()` 后包裹 `<span>`——文本节点本身保留，只插入标记。这样撤销 = 移除 `<span>` 并 `normalize()`。

（这条是我读代码发现的，不是实测，需要真机验证。）

### P2 — 差异化（决定它是不是"又一个工具"）

基于 `docs/市场调研.md` 的结论：**切分本身没有护城河，价值必须落在"可测量的进步"上。**

| 优化 | 为什么 |
|---|---|
| **自适应粒度** | 按用户水平/文本难度调 chunk 大小。这是 LLM 相对规则引擎唯一不可替代的地方——规则引擎做不了个性化 |
| **前后测（WPM + 理解正确率）** | 没有数字，用户感知不到价值，也就不会留存和付费 |
| **卡住的意群 → 次日复现** | 从"查看器"变成"训练器"的最小闭环 |
| **只做长难句场景** | 考研/雅思长难句是有明确痛点和付费意愿的窄口，避开与沉浸式翻译的正面对撞 |

### P3 — 工程健康

| 优化 | 说明 |
|---|---|
| `MAX_CONCURRENCY` 可配 | 现在硬编码 6。不同 Provider 的 RPM 差异极大，应作为 `ChunkOptions` 传入 |
| `SEGMENT_TARGET_CHARS` 自适应 | 现在固定 400。应按 Provider 的固定开销/吞吐特性调整 |
| token 成本可见 | 并发让 prompt token 翻 2–3 倍，应该把 `tokenUsage` 显示给用户 |
| engine 抽 `LlmTransport` 接口 | 现在 `client.ts` 直接 `fetch`。抽一层才能塞 Gemini Nano、本地 ONNX、mock |
| 真机验证 DOM 改写 | 见 P1 的 `applyHighlight` 缺陷，需要在 React/Shadow DOM 站点上验证 |

## 3. 一个被忽略的架构机会：Chrome 内置 Prompt API

`engine` 目前把"LLM"焊死在 OpenAI 兼容的 HTTP 协议上。但 Chrome 138+ 的扩展可以直接用 `LanguageModel`（Gemini Nano），**本地、免费、无需 Key、离线**。

这不是替换，而是**降级链**的一环：

```
1. 规则法        → <10ms，永远可用
2. Gemini Nano   → 100–500ms，本地，无成本
3. 云端 LLM      → 2s，质量最好
```

这个链条一旦成立，"要 Key / 要联网 / 会 429 / 隐私"四个问题同时消失。

实现只需要：`engine` 抽个 `LlmTransport` 接口，`client.ts` 变成它的一个实现，再加一个 `nanoTransport.ts`。**这是我认为架构上最值得做的一次投资。**

---

## 4. 不建议做的事

- **不要做生词本**。Relingo / Burning Vocabulary / LingoWay / 沉浸式翻译已饱和，且与"意群"是两个心智。
- **不要先搭后端代理**。在需求未被验证前，服务器成本是纯负债。Gemini Nano 已经免费解决了"免配置"这个需求。
- **不要做通用"任意网页"**。正面撞 TempoLeaf（41 用户）和沉浸式翻译（3000 万用户），两边都打不过。
- **不要继续调 prompt 追质量**。已实测：加一条字数约束就能从"按句切"变成 3.4 词/chunk，剩下的边际收益极小。

---

## 5. 如果只做三件事

按投入产出比排序：

1. **规则法秒出 + LLM 异步覆盖**（P0-1）——把感知延迟从 2s 打到 <10ms，这是唯一能改变产品性质的一步。
2. **缓存**（P0-3）——1 小时工作量，阅读场景命中率高，直接省掉大部分调用。
3. **抽 `LlmTransport` 接口 + 接 Gemini Nano**（P3 + 第 3 节）——一次性解决 Key / 联网 / 429 / 隐私四个问题。

第 1 条和第 3 条合起来，就把"一个要等 2 秒、要 Key、会限流的 LLM 封装"变成了"一个瞬间响应、离线可用、隐私安全的阅读辅助"。**这才是这个项目唯一可能有差异化的形态。**

---

## 6. 关于本轮已完成的并发

给一个诚实的评价：**并发是对的工程，但不是对的优先级。**

- 它解决了一个真实且严重的问题：>5k 字符时单请求会因输出截断而**彻底失败**（实测 12911 字直接 `INVALID_RESPONSE`）。这一条足以证明它该做。
- 但它对延迟的改善（1.1–1.25×）远低于直觉预期，因为瓶颈是固定开销而非吞吐。
- 代价是 token 翻 2–3 倍。

如果目标是"长文章不挂"，已达成。如果目标是"快"，它帮不上忙——那要靠 P0-1 和 P0-2。
