# Chunkly 优化清单（第一性原理视角）

> 日期：2026-10-20
> 前置阅读：`docs/市场调研.md`（结论：作为独立 C 端产品没有价值，建议换定位）
> 本文回答的是另一个问题：**如果继续做，从第一性原理看，还有哪些优化？**

---

## 0. 先问：这个系统真正要交付的是什么？

把这个产品剥到最里层，它承诺的只有一件事：

> **让读者在 100ms 内、在原文位置上、看到「按意群分组」的视觉提示，且原文一个字都不能变。**

注意这句话里有三个不可让步的约束：**快**（100ms 量级）、**原位**（不能跳去另一个阅读器）、**无损**（不能改写文本）。所有优化都可以拿这三条来打分。

对照现实：

| 约束 | 现状 | 差距 |
|---|---|---|
| 原位 | ✅ 原文 DOM 高亮 | 已满足 |
| 无损 | ✅ 游标 `indexOf` + 段拼回 + 空白归并 | 已满足，且有 39 个测试守着 |
| **快** | ❌ **1.9–2.6s（单句）/ 3–16s（长文）** | **差 20–100 倍** |

**所以第一性原理下的唯一真问题是：为什么一个阅读辅助工具要等 2 秒？**
其余所有优化（UI、闭环、多端）都在这个问题之下。

---

## 1. 延迟的物理下限：拆开每一毫秒

实测一个 297 字符请求 1967ms（`effort=off`、0 reasoning token、输出约 100 token）。这个数字本身就是诊断：

- 一个 flash 级模型生成 100 token，正常应该 300–600ms。
- 所以 **约 1.4–1.7s 花在别处**：网络 RTT、网关排队、Provider 调度。
- 这也解释了为什么并发只提速 1.1–1.25×：**并发摊薄不了固定开销**，而固定开销才是主体。

推论（这就是第一性原理给出的答案）：

| 方案 | 理论延迟 | 能否满足 100ms | 结论 |
|---|---|---|---|
| 调 prompt / 换模型 | 1.5–4s | ❌ | 只改常数，不改数量级 |
| 分段并发 | 1–16s | ❌ | 已做，解决的是可靠性不是延迟 |
| **流式渲染（streaming）** | **首字实测 2410ms** | ❌ | **实测证伪：开销在生成之前，流式摊薄不了** |
| 缓存（同文本复用） | 0ms | ✅ | **实测 1638ms → 5ms（327×）**，已实现 |
| 规则法秒出 + LLM 异步覆盖 | 首屏 <10ms | ✅✅ | **唯一能满足 100ms 的架构** |
| Chrome 内置 Prompt API（Gemini Nano） | 本地，待测 | ⚠️ | 无 Key、无网络、无成本 |

### 1.1 实测：2.4s 是恒定前置开销，与输出长度无关

这一组数据推翻了「靠流式或换模型能压延迟」的直觉（2026-10-20，CommandCode / `deepseek-v4.1-flash` / `effort=off`）：

| 测量 | 结果 |
|---|---|
| 37 字符串句，3 次总耗时 | 2491 / 2440 / 2347 ms |
| 300 字长句，3 次总耗时 | 2097 / 2583 / 2363 ms |
| 流式：首字 vs 总时长 | 2410 ms vs 2522 ms |
| 单 token 输出请求（`max_tokens:3`） | 2241 ms |
| `GET /models`（无生成） | 533 ms（curl，含 TLS 384ms） |
| `ping api.commandcode.ai` | RTT 280 ms |

**结论：存在约 2.2–2.4s 的恒定前置开销，且它与输出长度无关。**
拆解：网络往返约 0.5s（TLS 384ms + RTT 280ms），其余约 1.7s 在 provider 侧（调度/排队/预热）。

由此得到两个反直觉但关键的推论：

1. **流式无用。** 首字 2410ms ≈ 总时长 2522ms——生成只占 100ms 左右，开销全在生成开始之前，所以“边收边渲染”省不下首屏时间。
2. **并发无用（对延迟）。** 实测 1.1–1.25×：并发摊薄不了每请求的固定开销。

**唯一能进 100ms 的路径是「不发请求」。** 这直接决定了 P0 的优先级：缓存 > 本地推理，而不是流式。

## 2. 优化清单（按"是否影响生死"排序）

### P0 — 影响生死

#### P0-1　用规则法先秒出，LLM 异步覆盖（架构级）

这是唯一能同时满足"快"和"准"的方案，也是我上一轮调研里已经点出但没实现的方向。

```
点击/选中
  └─ <10ms：规则法（compromise + 标点/虚词规则）先渲染一版
       └─ 后台：LLM 切分完成 → 平滑替换为更准的版本
```

- 用户立刻看到东西，感知延迟 <10ms。
- LLM 慢不再是缺陷，而是"渐进增强"。
- 顺带解决离线、断网、Key 失效、429 全部场景——**降级路径天然存在**。
- 成本：需要引入 `compromise`（TempoLeaf 用的同一个库，MPL-2.0，可参考其规则）。
- **这是我认为最该做的下一步。**

#### P0-2　~~流式渲染~~（已实测证伪，不推荐）

我原来建议「改流式，首字节从 1967ms 降到约 400ms」。**实测后这个判断是错的**：首字 2410ms、总时长 2522ms，生成只占约 100ms，开销全在生成开始之前。

流式做不到「更早看到第一个意群」，只能做到「边收边渲染后面的」。对 6 个 chunk 的典型输出而言，感知提升接近零，但代码复杂度显著上升（增量 JSON 解析器、部分 Provider 不支持流式 + json_object）。

**不做，除非将来 provider 侧的排队开销消失。**

#### P0-3　缓存（1 小时工作量，收益最大）

阅读场景的重复率被严重低估：同一篇文章反复打开、翻页回来、同一段被重新选中。

- 以 `hash(text + model + effort + granularity)` 为 key，存 `chrome.storage.local`。
- 命中即 0ms、0 成本。对"读一篇文章"这个场景，命中率会很高。
- 需要注意：`chrome.storage.local` 默认 10MB（`unlimitedStorage` 可解），要设 LRU 上限。

### P1 — 及格线（现在缺的）

| 项 | 现状 | 说明 |
|---|---|---|
| **流式/加载态** | 只有 toast「切分中…」 | 无法取消，无进度。需要 AbortController 接到 UI 上 |
| **快捷键触发** | 只有右键菜单 | `chrome.commands` 加一条，5 行代码 |
| **重试** | engine 内部有，插件侧无 | 已被并发路径覆盖；短文本路径仍无重试 |
| **跨段落/多行选区** | 只取第一个 Range | 阅读场景里跨段落选中是常态，当前静默失败 |
| **切换粒度** | `granularity` 在 engine 有，UI 没有 | 一行设置项 |
| **清除高亮** | 没有 | 用户标完想还原，现在只能刷新页面 |
| **撤销** | 没有 | `range.deleteContents()` 是有损操作，改坏了无法恢复 |

#### 一个必须正视的实现缺陷

`highlight.ts` 的 `applyHighlight` 用 `range.deleteContents()` + `insertNode()` **替换了原始 DOM 文本节点**。

后果：
1. 破坏了页面自身的 DOM 结构（React/Vue 站点可能重渲染导致错乱）。
2. 无法撤销（原始节点已销毁）。
3. 对 `contenteditable`、React 受控组件、Shadow DOM 会出问题。

更稳的做法：不删节点，用 `Range.surroundContents()` 或对文本节点做 `splitText()` 后包裹 `<span>`——文本节点本身保留，只插入标记。这样撤销 = 移除 `<span>` 并 `normalize()`。

（这条是我读代码发现的，不是实测，需要真机验证。）

### P2 — 差异化（决定它是不是"又一个工具"）

基于 `docs/市场调研.md` 的结论：**切分本身没有护城河，价值必须落在"可测量的进步"上。**

| 优化 | 为什么 |
|---|---|
| **自适应粒度** | 按用户水平/文本难度调 chunk 大小。这是 LLM 相对规则引擎唯一不可替代的地方——规则引擎做不了个性化 |
| **前后测（WPM + 理解正确率）** | 没有数字，用户感知不到价值，也就不会留存和付费 |
| **卡住的意群 → 次日复现** | 从"查看器"变成"训练器"的最小闭环 |
| **只做长难句场景** | 考研/雅思长难句是有明确痛点和付费意愿的窄口，避开与沉浸式翻译的正面对撞 |

### P3 — 工程健康

| 优化 | 说明 |
|---|---|
| `MAX_CONCURRENCY` 可配 | 现在硬编码 6。不同 Provider 的 RPM 差异极大，应作为 `ChunkOptions` 传入 |
| `SEGMENT_TARGET_CHARS` 自适应 | 现在固定 400。应按 Provider 的固定开销/吞吐特性调整 |
| token 成本可见 | 并发让 prompt token 翻 2–3 倍，应该把 `tokenUsage` 显示给用户 |
| engine 抽 `LlmTransport` 接口 | 现在 `client.ts` 直接 `fetch`。抽一层才能塞 Gemini Nano、本地 ONNX、mock |
| 真机验证 DOM 改写 | 见 P1 的 `applyHighlight` 缺陷，需要在 React/Shadow DOM 站点上验证 |

## 3. 一个被忽略的架构机会：Chrome 内置 Prompt API

`engine` 目前把"LLM"焊死在 OpenAI 兼容的 HTTP 协议上。但 Chrome 138+ 的扩展可以直接用 `LanguageModel`（Gemini Nano），**本地、免费、无需 Key、离线**。

这不是替换，而是**降级链**的一环：

```
1. 规则法        → <10ms，永远可用
2. Gemini Nano   → 100–500ms，本地，无成本
3. 云端 LLM      → 2s，质量最好
```

这个链条一旦成立，"要 Key / 要联网 / 会 429 / 隐私"四个问题同时消失。

实现只需要：`engine` 抽个 `LlmTransport` 接口，`client.ts` 变成它的一个实现，再加一个 `nanoTransport.ts`。**这是我认为架构上最值得做的一次投资。**

## 4. 不建议做的事

- **不要做生词本**。Relingo / Burning Vocabulary / LingoWay / 沉浸式翻译已饱和，且与"意群"是两个心智。
- **不要先搭后端代理**。在需求未被验证前，服务器成本是纯负债。Gemini Nano 已经免费解决了"免配置"这个需求。
- **不要做通用"任意网页"**。正面撞 TempoLeaf（41 用户）和沉浸式翻译（3000 万用户），两边都打不过。
- **不要继续调 prompt 追质量**。已实测：加一条字数约束就能从"按句切"变成 3.4 词/chunk，剩下的边际收益极小。

---

## 5. 如果只做三件事

按投入产出比排序：

1. **规则法秒出 + LLM 异步覆盖**（P0-1）——把感知延迟从 2s 打到 <10ms，这是唯一能改变产品性质的一步。
2. **缓存**（P0-3）——1 小时工作量，阅读场景命中率高，直接省掉大部分调用。
3. **抽 `LlmTransport` 接口 + 接 Gemini Nano**（P3 + 第 3 节）——一次性解决 Key / 联网 / 429 / 隐私四个问题。

第 1 条和第 3 条合起来，就把"一个要等 2 秒、要 Key、会限流的 LLM 封装"变成了"一个瞬间响应、离线可用、隐私安全的阅读辅助"。**这才是这个项目唯一可能有差异化的形态。**

## 6. 关于本轮已完成的并发

给一个诚实的评价：**并发是对的工程，但不是对的优先级。**

- 它解决了一个真实且严重的问题：>5k 字符时单请求会因输出截断而**彻底失败**（实测 12911 字直接 `INVALID_RESPONSE`）。这一条足以证明它该做。
- 但它对延迟的改善（1.1–1.25×）远低于直觉预期，因为瓶颈是固定开销而非吞吐。
- 代价是 token 翻 2–3 倍。

如果目标是"长文章不挂"，已达成。如果目标是"快"，它帮不上忙——那要靠 P0-1 和 P0-2。

## 7. 已落地（2026-10-20）

按本文档执行后已完成的部分，以及**与原文预测不符、被实测推翻**的部分。

### 7.1 已完成

| 项 | 结果 | 证据 |
|---|---|---|
| ADR-0001：高亮保留原始 DOM 节点 | ✅ | 12 个 DOM 测试；`isConnected` 断言 |
| 撤销高亮 | ✅ | `Alt+Shift+Z` + 右键菜单，真机还原验证 |
| 缓存 | ✅ | **1638ms → 5ms（327×）** |
| 跨段落选区 | ✅ | 跨两个 `<p>` 正确高亮，块级结构不破坏 |
| **规则法秒出 + LLM 覆盖（P0-1）** | ✅ | **首屏 5ms，LLM 2405ms 接管（481×）** |

### 7.2 被实测推翻的判断（重要）

我在这份清单里写过两个**后来被数据否掉**的结论，留在这里作为记录：

**① 「流式能把首字节降到 300–500ms」——错。**

实测：首字 2410ms，总时长 2522ms。生成只占约 100ms，开销全在生成**开始之前**。
更关键的证据：37 字符串句与 300 字长句的总耗时都是约 2.4s——**延迟与输出长度无关**，
是一个恒定前置开销（网络 0.5s + provider 侧约 1.7s）。

推论：流式救不了首屏；并发也救不了（实测 1.1–1.25×，因为摊薄的只是生成时间，不是前置开销）。

**② 「规则法只是兜底，质量不够看」——低估了它。**

实测同一段落：

| | 延迟 | chunks | 平均词/意群 | 无损 |
|---|---|---|---|---|
| LLM | 3343ms | 11 | 4.9 | ❌ 该次丢了字符 |
| 规则法 | **0.50ms** | 10 | 5.4 | ✅ |

规则法切得确实略粗，但**在"立刻能用"这件事上它是唯一解**，而且这次它比 LLM 更可靠。

### 7.3 因此修正后的优先级

原清单把"流式"列为 P0-2。**现已降级为"不做"**。

真正有效的顺序是：

1. ✅ 缓存（0ms，命中即免费）
2. ✅ 规则法秒出 + LLM 覆盖（首屏 5ms）
3. ⬜ Chrome 内置 Prompt API（Gemini Nano）——把 2405ms 也干掉，同时解决 Key/联网/隐私
4. ⬜ 自适应粒度、可测量的训练闭环（决定它是不是"又一个工具"）

### 7.4 规则法的已知局限

诚实记录，免得以后误以为它够用：

- 切得偏粗（平均 5.4 词/意群 vs LLM 的 4.9），复杂句上偶有 `which was published last year, argued that` 这类跨句读起来别扭的组合。
- 手写规则 + 词表，覆盖不到所有结构。已知未处理：倒装、省略、长名词短语内部边界。
- 但**无损契约与 LLM 路径同等严格**，有 18 个测试守着（含"不许碎成逐词"的回归测试）。

## 8. Gemini Nano 实测：结论是「不接」

文档第 3 节建议「抽 `LlmTransport` + 接 Gemini Nano，一次性解决 Key/联网/429/隐私」。**实测后这个建议不成立**，记录数据与原因。

### 8.1 事实核对（先说清环境）

| 项 | 结果 |
|---|---|
| `LanguageModel` 在**扩展 service worker** 里可用？ | ✅ `typeof = function`（官方文档说的「Web Workers 不可用」不含扩展 SW） |
| 硬件是否满足 | ✅ macOS 27 / 16GB RAM / 10 核 / 308GB 空闲 |
| 真实 Chrome 155 + 真实 HTTPS origin | ✅ `availability = "downloadable"` → 下载后 `available` |
| Chrome for Testing | ❌ `availability = "unavailable"`（CfT 不附模型，软链接 4GB 模型也无效） |
| Chrome 155 命令行加载未打包扩展 | ❌ 已被禁用（`--load-extension` 无效，`Extensions.loadUnpacked` 也不可用） |

**验证方法**：用真实 Chrome + CDP，在 `https://example.com` 页面上下文实测。

### 8.2 Nano 实测数据（真实 Chrome 155，297 字 / 152 字段落）

| 指标 | Gemini Nano | 云端 deepseek-v4.1-flash |
|---|---|---|
| 延迟 | 1454–2123ms | 2405ms |
| **平均词/意群** | **2.0–2.8（太碎）** | 4.9–5.4（合适） |
| 输出是否符合格式 | ❌ 必定包 ``` 代码块 | ✅ |
| 输出是否无损 | ❌ **吞掉切分处空格** | ⚠️ 偶发（一次丢了字符） |
| 首次准备 | **813757ms（13.5 分钟）** | 0 |
| contextWindow | 9216 | 128k |
| 需下载 | 4GB 模型 | 0 |

**决定性的一条是粒度。** Nano 平均切出 2.0–2.8 词/意群，而意群切分的目标是 2–6 词、
实际应以 4–5 词为主（低于 3 词会把读者打回逐词阅读，正是要治的病）。
延迟也没有优势（1.5–2.1s vs 2.4s，同一个数量级），却换来 4GB 下载、13.5 分钟首次准备、
9216 context 上限。

### 8.3 Nano 吞空格：顺手修掉了一个真 bug

实测 Nano 的输出：

```
["She put","the keys","on the","table by","the door."]
拼回 = "She putthe keyson thetable bythe door."   ← 空格被吞
```

**但真正的收获不是 Nano，而是这暴露了 `parse.ts` 的一个静默 bug**：
`tryLocateExactly` 只检查「每个 chunk 都是原文子串」，**不检查拼起来是否覆盖整段原文**。
Nano 的每个 chunk 单独看确实都在原文里，于是全部匹配成功、静默返回——
结果是高亮 offset 与原文对不上，且**不报错**。

已修：精确路径现在要求拼接结果严格等于原文，否则降级到吸附。

### 8.4 保留的产出：切点吸附

即使不接 Nano，吸附算法本身值得留着——它让**任何** provider 的输出都更安全
（云端也丢过一次字符）。做法：

1. 前置校验：模型输出**去掉所有空白**后必须与原文去空白后完全一致。
   这条把「只是空白没处理好」和「模型改写了内容」分开——前者可修，后者必须报错。
2. 把模型输出当作「切点提示」，在每个提示位置附近（±24 字符）寻找最近的词边界。
3. **从原文切片**，而不是用模型给的字符串。

因此 `parseChunkResponse` 的输出永远满足「拼回等于原文」，与模型守不守约无关。

### 8.5 结论

**不接 Gemini Nano。** 理由按权重排序：

1. 粒度不对（2 词/意群 vs 需要的 4–5 词），这是产品核心指标，不是可调参数
2. 延迟同数量级，没有值得换来 4GB 下载 + 13.5 分钟首次准备的收益
3. 隐私/免 Key 的价值真实，但 `availability` 在大量设备上是 `unavailable`，
   把它当我产品的主路径会让一半用户装上就用不了
4. 它的失败反而帮我发现了 `parse.ts` 的真 bug —— 这一趟没白跑

**如果将来 Nano 把粒度调好，接入成本已经很低**：`parse.ts` 的吸附已就绪，
剩下的只是抽 `LlmTransport` 接口。

## 9. 本地网关模型测速（2026-10-21）

用户反馈「切分还是太慢」，要求测本地网关里的快速模型。测法：同一 340 字段落、
同一 prompt、每模型 3 次取中位；判定「可用」= 原始无损，或经 `parse.ts` 的切点吸附后无损。

| 模型 | 中位延迟 | 可用 | 粒度 |
|---|---|---|---|
| **claude-haiku-5-5** | **1234ms** | 3/3 | 9 chunks / 5.8 词（max 8）|

**结论：`commandcode-plan/claude-haiku-5-5`**，已设为 `LOCAL_PRESET` 的默认模型。

2. **`deepseek-v4.1-flash-fast` 名不副实**：中位 4421ms，比非 fast 版还慢。

## 10. 设置页重构（官方 / 自定义二分）

用户反馈：「无法修改模型并保存」，要求重构设置页，且指出**插件对外开放就不能使用本地网关**。

### 10.1 「改了模型但保存不了」的根因（我自己引入的回归）

修 401 时我加了「预设说了算」：

```js
if (presetId !== "custom") {
  return { provider: { ...PRESETS[presetId], apiKey: provider.apiKey } };
  //                        ↑ 用预设值覆盖用户改的 model
}
```

保存时确实写进了存储（`z-ai/glm-5.3-flash`），但**重新打开设置页时被
`normalizeSettings` 改回默认**。存储里是对的、界面显示是错的，所以用户看到
「改了没用」。

教训：修一个 bug 时引入的「不变量」如果过宽，会吃掉用户的合法输入。
现在把职责拆清楚：

- **端点**由模式决定（官方模式固定为官方地址，残留地址不会导致 401）
- **模型**是用户的选择，必须尊重，只在为空时回落默认
- **apiKey** 永远尊重

### 10.2 新结构：官方 / 自定义

删掉「本机网关」预设——**插件对外发布后，让用户配 `127.0.0.1:3425` 毫无意义**，
只会造成困惑。本地网关是开发期便利，不是产品功能。

| 模式 | 用户要填 | 模型选择 |
|---|---|---|
| **官方** | 只有 Key | 三选一 |
| **自定义** | 地址 + Key + 模型名 | 任意 |

官方可选模型（CommandCode 直连，2026-10-21 实测均可用，96 个模型里选的三个）：

| 模型 | 说明 |
|---|---|
| `z-ai/glm-5.3-flash` | 默认。中文语感好，速度与粒度平衡 |
| `deepseek/deepseek-v4.1-flash` | 切分更细（约 4 词/意群） |
| `gpt-5.6-luna` | 粒度居中，稳定性好 |

只给三个下拉、不给自由输入：新用户不会填错一个不存在的模型名而卡在报错上。
想试别的模型的人走「自定义」。

### 10.3 移除推理强度选项

不再暴露 `reasoning_effort`。理由是我测出来的一个反直觉结论：

| 模型 | 关 thinking |
|---|---|
| CommandCode deepseek-v4.1-flash | 3974ms → 1967ms（**快一倍**）|
| claude-haiku-5-5 | 1234ms → 2847ms（**慢一倍**）|

「关 thinking 总是更快」是错的，因模型而异。把这个取舍丢给用户是设计缺陷，
所以统一**不传**推理相关参数，让各模型走自己的默认。

### 10.4 验证（真实 Chrome）

```
初始：模式=official，模型三选一，默认 glm-5.3-flash，无本地网关字样，提示 ⌘⇧C
保存 deepseek → 已保存
重开设置页  → 模型仍是 deepseek ✅（bug 已修）
测试连接    → 连接正常（2265ms）
切自定义    → 官方面板隐藏，自定义面板显示
真实切分    → gpt-5.6-luna：4685ms / 3398ms，结果无损
```

## 11. 「切分失败」的真因：Service Worker 的 30 秒 fetch 上限

用户报「显示切分失败请重试」。直连测试三个模型全部成功，但在扩展里实测GLM处理
683 字文本用了 **43.8 秒** —— 这撞上了一条我们之前完全没考虑的硬限制。

Chrome 官方文档（service worker lifecycle）明确写着，以下情况会**终止** SW：

> - After 30 seconds of inactivity.
> - When a single request, such as an event or API call, takes longer than 5 minutes.
> - **When a `fetch()` response takes more than 30 seconds to arrive.**

SW 被杀 → 消息通道断开 → 用户只看到「切分失败」，真正的原因（模型太慢）不可见。
**这是最坏的错误形态：原因不可见。**

修法两层：

1. `client.ts` 加 25s 主动超时（`AbortSignal.timeout` + 与外部 signal 合并）。
   主动中止能给出可读的 TIMEOUT 错误，比 SW 被杀的静默失败可控。
2. **把延迟压到远低于 30s** —— 见下。

## 12. 推理强度必须按模型写死（4.4 倍差异）

之前我删掉了 reasoning_effort 选项，并且**完全不传**。这是错的：不传时模型会
自行决定，多数模型选择大量 thinking。

实测（2026-10-21，CommandCode，~400 字段落，各 3 次取中位）：

| 模型 | 配置 | 中位延迟 | reasoning tokens | 粒度 |
|---|---|---|---|---|
| deepseek-v4.1-flash | **off** | **2340ms** | 0 | 14ch / 3.4w |
| deepseek-v4.1-flash | low | 5996ms | 529 | 14ch / 3.4w |
| gpt-5.6-luna | low | 4301ms | 115 | 11ch / 4.3w |
| gpt-5.6-luna | 不传 | 5254ms | 233 | 11ch / 4.3w |
| glm-5.3-flash | low | 4790ms | 0 | 9ch / 5.2w |
| glm-5.3-flash | 不传 | **10368ms** | 449 | 12ch / 3.9w |

**差异 4.4 倍。** 切分是浅层句法任务，thinking 纯浪费。

但**支持的取值因模型而异**：CommandCode 上 `reasoning_effort: "off"` 只有部分模型
接受，传给 `z-ai/glm-5.3-flash` 直接 **HTTP 400**（`none` 也一样 400）。
所以 effort 必须**逐模型配对写死**，不能全局设一个，也不能暴露给用户。

已在 `types.ts` 的 `OFFICIAL_MODELS` 里逐项标注 `effort`，默认模型改为
`deepseek/deepseek-v4.1-flash`（最快且粒度最接近意群阅读推荐值）。

## 13. 切点吸附救了「空格丢失」

上表里 `off` / `low` 的原始输出经常不是逐字符无损——但**差异只是 chunk 之间
丢了空格**，字符本身没错：

```
原文: "... you can switch on. It is a habit ..."
拼回: "... you can switch on.It is a habi ..."    ← 只是少了空格
```

`parse.ts` 的切点吸附（第 8.4 节）正好处理这一类：去掉所有空白后与原文比对，
一致则把模型输出退化为「切点提示」，从原文切片。实测三种配置经吸附后**全部无损**。

也就是说：**吸附不是给 Nano 做的兼容层，它是让「关 thinking 换速度」这个优化
变得可行的前提。** 没有它，`off` 配置会被判定为 INVALID_RESPONSE。

## 14. 官方模式的 Key 不进设置页

用户指出：**不要把我的 API Key 放在设置页面上**。

这是对的，而且原来的做法有实质问题：设置页是用户可见、可读取的，
把开发者密钥放在那里等于交给每个用户。

现在：
- 官方模式**没有 Key 输入框**，页面也不出现 `user_` 字样，只提示「已内置额度」
- Key 由**构建时注入**（`vite.background.config.ts` 的 `define` +
  环境变量 `CHUNKLY_OFFICIAL_API_KEY`），只存在于打包后的 `background.js`
- `options.js` 产物里 grep 不到该 key（已验证为 0）
- 只有「自定义」模式下用户才填自己的 Key

构建命令：
```bash
CHUNKLY_OFFICIAL_API_KEY="user_..." pnpm --filter @chunkly/extension build
```
未配该变量时官方模式会返回 `NO_OFFICIAL_KEY`，提示用户改用自定义模式。

## 16. 400 被误报成「解析失败」——真正的 root cause

用户报「切分失败请重试」。这次彻底查清了：**不是 key 问题**
（文件里的 key 对 glm 和 deepseek 都返回 200，注入产物里的 key 也逐字节一致），
是 **`reasoning_effort` 配错了 + 400 被错误分类**。

### 16.1 各模型对 reasoning_effort 的支持矩阵（实测）

| 模型 | `off` | `low` | 不传 |
|---|---|---|---|
| `deepseek/deepseek-v4.1-flash` | ✅ 200 | ✅ 200 | ✅ 200 |
| `z-ai/glm-5.3-flash` | ❌ **400** | ✅ 200 | ✅ 200 |
| `gpt-5.6-luna` | ❌ **400** | ✅ 200 | ✅ 200 |

glm / luna 传 `off` 时服务端明确回：

```
Model "z-ai/glm-5.3-flash" does not support reasoning_effort "off"
```

我上一轮给 glm/luna 写死 `low` 是对的，但**默认模型选成了 deepseek**，
又在文档里写「默认 glm」——两边不一致，用户实际跑的是我改过的那版。

### 16.2 真正致命的是错误分类

`client.ts` 把 400 映射成 `INVALID_RESPONSE`，界面显示
「**切分结果解析失败，请重试**」。

这条提示把排查方向带偏了整整一轮：看起来像解析器 bug，实际是参数被拒。
现在 400 单独成 `BAD_REQUEST`，提示改成「模型拒绝了请求参数，请在设置页换一个模型」。

**教训：错误分类也是 API 的一部分。** 一个错误的 code 会让用户（和我）
在完全错误的地方找原因。凡是「原因不可见」的错误形态都要避免。

### 16.3 `response_format` 不是问题

一度怀疑 `response_format: json_object` 不被支持（早期矩阵测试确实出现过 400）。
复核后确认：**只要 effort 配对正确，三个模型带 `response_format` 全部 200**。
早期那次 400 是我 shell 转义把 JSON 弄坏了，不是服务端拒绝。

### 16.4 最终配置（按用户指定）

| 模型 | effort | 短句 | 长段 |
|---|---|---|---|
| `z-ai/glm-5.3-flash` **（默认）** | low | 4103ms | 3927ms |
| `deepseek/deepseek-v4.1-flash` | off | 1534ms | 2783ms |
| `gpt-5.6-luna` | low | 3798ms | 8643ms |

三个模型 × 短句/长段 = 6 种场景，**全部成功且无损**。

另外加了一道构建期校验：注入的 key 必须与源 key **逐字节相同**，
不一致则构建失败——上一轮曾出现过注入截断 key 导致 401 的情况。
